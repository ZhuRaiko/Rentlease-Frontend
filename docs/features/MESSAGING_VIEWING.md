## UC-09B rental reservations — local implementation, separate deployment required

IMPLEMENTED / AUTOMATED-TESTED locally; Android RUNTIME-UNVERIFIED. This supersedes older reservation-deferred statements below. Rental reservations are separate from viewing appointments: Schedule Viewing requests an inspection; Request Reservation requests a commitment for the intended rental period. No payment/deposit, auto-approval, listing status change, or automatic tenancy creation. A pending request never reserves the unit.

Entry: Contact Owner from shared real Listing Details opens/reuses a conversation, then Request Reservation opens its separate request/management flow. Owners have Reservation requests in that conversation. Chat inbox has Rental reservations across actual participant conversations. No new bottom tab; appointment/reservation editors use the existing nested Back and account-scoped workspace patterns, keyboard-aware notes, foreground/pull refresh and safe-area handling. UC-09A and UC-09B can be deployed independently; missing RPCs show a backend-update requirement rather than local success.

The requester chooses a future Philippine move-in date, 1–120 whole calendar months, and an optional 1,000-character message. End dates use calendar-month addition with month-end clamping; the commitment period includes move-in and ends at the beginning of the displayed end date. Owners approve/decline pending requests; either participant may cancel pending or approved commitments before expiration. Decisions are confirmed by protected server receipts and retain audit history. Notes, revision tokens and operation UUIDs handle concurrent changes and exact retry after uncertain outcomes. Back on an uncertain write offers retry or an explicit leave confirmation; refresh after leaving before another request. No persistent offline retry journal.

User-approved policy (November 6): pending requests expire after seven days or at move-in midnight in Asia/Manila, whichever comes first; approved commitments expire at the end of the requested rental period unless cancelled. Applicant identity is the neutral Renter label with actual Tier 1-active and Tier 2-approval flags. No display_name, avatar, contact information, private location, or invented identity is returned. The user explicitly chose neutral identity until a consented public name exists; no new consent/profile feature is included.

Server reads compute effective expiration even when the stored status has not been materialized as expired; no cron job is required. Server writes reject expired requests/commitments, and expire can materialize an already-due expiration for an eligible participant, never expire it early. Expired rows no longer block new requests or approvals. The UI uses returned server time to correct the display clock and a single deadline wake-up to refresh, plus ordinary refresh; no Realtime dependency or automatic retry/polling loop. Failed refresh is an error, not an empty result; successful cached records remain scoped to the account.

Architecture: `RentalReservation.ts` owns normalized contracts/date/status helpers; `reservationService.ts` owns typed RPCs, identity checks, cancellation/time bounds, strict parsing and safe errors; `reservationWorkflow.ts` owns state, requests, decisions, retry IDs, revisions, paging and stale/account cleanup; `useRentalReservationsViewModel.ts` owns lifecycle/expiry refresh. `RentalReservationsView` and `ReservationDateField` render data using shared controls and the existing native date picker. Views contain no Supabase client. Pending, Approved, and Past / closed filter the loaded 20-record pages with explicit Load more; last 100 audit events are displayed while all events persist.

Prepared [20261106121806_property_rental_reservations.sql](../../supabase/migrations/20261106121806_property_rental_reservations.sql) adds public.rental_reservations (RLS enabled, no client table privileges), a private rentlease_reservations event/projection schema, three authenticated-only empty-search-path RPCs, and one additive tenancy conflict trigger. The current physical property is the rentable unit: conflicts are enforced across different listings for the same property.

| Prepared RPC | Enforcement |
| --- | --- |
| request_rental_reservation(conversation, request UUID, move-in date, months, message) | Active Tier 1 renter participant; no self-request; IDs/owner derived from real conversation/listing/property; open conversation and active/published/property-owner-consistent listing, available by move-in; owner eligible; one active overlapping request per renter/property; duplicate UUID/payload reconciliation; existing open-tenancy and approved-reservation conflicts denied. |
| respond_rental_reservation(reservation, operation UUID, expected revision, action, note) | Actual eligible participant; only the actual current owner approves a pending request with eligible renter/listing, historical participant owner may decline/cancel; no ID/period reassignment; revision conflicts; exact retry receipt; approve/decline/cancel/expire transition checks; approved periods cannot overlap on one property. |

All writes require READ COMMITTED and take the same property advisory transaction lock used by existing property/identity/tenancy guards, followed by relevant row locks. The additive aac_reservation_tenancy_commitment trigger rejects an overlapping manual tenancy for a different renter/owner while an approved hold exists; a manually authorized tenancy for the same participants remains possible, retaining all existing version, identity and activation protections. Conversely reservation requests/approvals reject overlapping proposed/pending-confirmation/active tenancies, with an unknown tenancy end treated as open-ended. Existing tenancy dates are inclusive at their end; reservation end dates are exclusive. Actual concurrent approval and tenancy tests pass. Original UC-08/UC-09A functions, policies, role records, publication, verification, Admin and private document rules are unchanged.

Rollback is [feature-disable source](../../supabase/test-support/property_rental_reservations_rollback.sql): it removes only the three new public RPCs. Records/events/private helpers/indexes and the new tenancy conflict guard remain, so existing approved commitments are not silently abandoned. Any reenable or retirement requires a separately authorized recovery migration; do not replay the creation migration. No permanent live backend mutation was performed in this phase.
