Rental reservations are separate from viewing appointments: Schedule Viewing requests an inspection; Request Reservation requests a commitment for the intended rental period. No payment/deposit, auto-approval, listing status change, or automatic tenancy creation. A pending request never reserves the unit.

Entry: Contact Owner from shared real Listing Details opens/reuses a conversation, then Request Reservation opens its separate request/management flow. The requester chooses a future Philippine move-in date, 1–120 whole calendar months, and an optional 1,000-character message. End dates use calendar-month addition with month-end clamping; the commitment period includes move-in and ends at the beginning of the displayed end date. Owners approve/decline pending requests; either participant may cancel pending or approved commitments before expiration. Decisions are confirmed by protected server receipts and retain audit history. Notes, revision tokens and operation UUIDs handle concurrent changes and exact retry after uncertain outcomes. Back on an uncertain write offers retry or an explicit leave confirmation; refresh after leaving before another request. No persistent offline retry journal.

User-approved policy (November 6): pending requests expire after seven days or at move-in midnight in Asia/Manila, whichever comes first; approved commitments expire at the end of the requested rental period unless cancelled. Applicant identity is the neutral Renter label with actual Tier 1-active and Tier 2-approval flags. No display_name, avatar, contact information, private location, or invented identity is returned. The user explicitly chose neutral identity until a consented public name exists; no new consent/profile feature is included.

Server reads compute effective expiration even when the stored status has not been materialized as expired; no cron job is required. Server writes reject expired requests/commitments, and expire can materialize an already-due expiration for an eligible participant, never expire it early. Expired rows no longer block new requests or approvals. The UI uses returned server time to correct the display clock and a single deadline wake-up to refresh, plus ordinary refresh; no Realtime dependency or automatic retry/polling loop. Failed refresh is an error, not an empty result; successful cached records remain scoped to the account.

Architecture: `RentalReservation.ts` owns normalized contracts/date/status helpers; `reservationService.ts` owns typed RPCs, identity checks, cancellation/time bounds, strict parsing and safe errors; `reservationWorkflow.ts` owns state, requests, decisions, retry IDs, revisions, paging and stale/account cleanup; `useRentalReservationsViewModel.ts` owns lifecycle/expiry refresh. `RentalReservationsView` and `ReservationDateField` render data using shared controls and the existing native date picker.
