# Reporting and Admin moderation

## Status - November 11, 2026

IMPLEMENTED LOCALLY / focused frontend AUTOMATED-TESTED / RUNTIME-UNVERIFIED on `feature/reporting-moderation`. Backend migration is PREPARED, NOT DEPLOYED. No production report was created or moderated.

## Behavior and integration

Real Rental Details offers Report this listing. An actual messaging conversation offers Report participant; the server derives the counterpart rather than trusting a user ID. Reasons and optional explanation require explicit submission. Ratings & Reports opens My submitted reports with persistent statuses, paging and safe resolution summaries. Reports are confidential: the target cannot read them merely because they are reported.

Admin Dashboard and queue use real counts and listing/user/status filters. Independent active Tier 1 Admins can inspect context, begin review, dismiss, or resolve a substantiated report. A private decision note is required; an optional separately labeled public-safe summary is visible to the reporter. No report action changes publication, accounts, verification or tenancy. Reporter, target, captured parties, current property owner and actual property tenancy participants cannot moderate their own related cases. Existing review moderation remains separate.

## Architecture and recovery

Shared `Reporting.ts` models, `reportingService.ts`, `reportingWorkflow.ts`, `useReporting.ts` and `Reporting.tsx` own the reusable flow. Views call workflows, not Supabase. Actual account checks surround transport; account/source keys, aborts, generation guards and bounded timeouts prevent stale publication. Saving blocks duplicate submissions and Back. Uncertain outcomes retain the exact operation for explicit retry; definitive rejections reload authoritative state. Moderation receipts acknowledge the original operation separately from the current case, allowing reconciliation after another Admin advances it.

The account/source-scoped AsyncStorage journal temporarily contains report text or private Admin notes. It is app-private storage, not an encrypted vault; no encryption guarantee, credentials or automatic offline retry is added. Keep app data until uncertain actions reconcile. Pagination is 20 rows with maximum offset 10,000; Admin history is the latest 20 immutable events.

## Admin Actions and Audit - November 13, 2026

**Status:** IMPLEMENTED and AUTOMATED-TESTED in the frontend; the backend migration `supabase/migrations/20261113180000_admin_actions_audit.sql` was APPLIED to the hosted project on 2026-11-13 (see the ledger, HOSTED_MIGRATION entry) and its catalog state was verified read-only. Android runtime against the hosted backend is UNVERIFIED: no Admin action, audit-log read or restrictions read has been exercised on the hosted project yet. The audit log also hides rows of any report the calling Admin is conflicted on. Backend ledger: [REPORTING_MODERATION_BACKEND_LEDGER.md](../implementation-reports/database/REPORTING_MODERATION_BACKEND_LEDGER.md) (entry ADMIN-ACTIONS-AUDIT-2026-11-13). Design evidence: [admin-actions-audit-skill-passes.md](../implementation-reports/ui/admin-actions-audit-skill-passes.md).

**Behavior.** Actions tab lists currently suspended or restricted accounts (status, reason, end date with an "Ended, restore" flag once the date has passed); opening one allows Restore with a required reason (10 to 500 characters). From an upheld report, "Take action" offers Suspend user (user report) or Remove listing (listing report) with a reason, an optional end date for suspensions (7, 30, 90 days or none), and a plain-language statement of the effect. Audit tab shows the real audit log newest first with All, Verification, Reports, Actions and Reviews filters and 25-per-page paging; the dashboard shows the three newest decisions. Warn and Restrict are not wired. An end date is a reminder only: nothing restores an account automatically (no scheduler exists), so the UI says so.

**Architecture.** View to ViewModel (`useAdminModerationViewModel`) to `adminActionsWorkflow.ts` (framework-free state, generation guards, one decision at a time, exact-retry attempts) to `adminActionsService.ts` (three RPCs: `apply_admin_moderation_action`, `get_admin_restrictions`, `get_admin_audit_log`). Errors use the shared `AdminOperationError` mapper; a drift-guard test compares every message the SQL raises with the mapper's rules, plus parameter names, bounds, page sizes and filters. After an unknown outcome (network, timeout, unknown error) a retry reuses the same operation id and end date, so the server replays the stored result instead of acting twice; any edit starts a new attempt. The operation id is held in memory, not persisted: after an app restart a retry is a new operation, which the server's state checks refuse if it already took effect.

**Backend contract (prepared).** Each RPC requires `is_active_admin(auth.uid())`. Actions are suspend, restore and remove (pause is not offered, see below), inserted into `moderation_actions` so the existing `trg_apply_moderation_action` applies the effect and writes the audit row. Validation: reason length, one target of the right kind, no self or Admin targets, end date only on suspension and in the future, suspend only an active account, restore only a suspended or restricted one, remove only an active or paused listing and never while a tenancy is proposed, awaiting confirmation or active, suspend and remove REQUIRE a report (restore may omit it), and a report must exist, not conflict with the Admin, be upheld and match the target. Idempotent per actor and operation id through a private receipts table. Additive audit triggers record verification decisions, report decisions and review moderation decisions (entity, status, the Admin's reason or note only). Audit writes are strict: an audit failure rolls back the decision.

**Verification.** 117 container checks (see `supabase/test-support/ADMIN_ACTIONS_AUDIT.md`) and the frontend tests `adminActions`, `adminActionsWorkflow`, `adminActionsService` and `adminActionsErrorDrift`. Android: agent-observed only (the live "Backend update needed" states, and populated screens from a temporary in-memory sample service that is not in the repository). Not verified: the hosted RPCs, TalkBack, dark theme, tablet, and the report-to-action flow on a real upheld report.

**Pause is deliberately not wired (future work).** The live `reactivate_listing` lets the listing owner undo any paused listing, so an Admin pause would not be enforceable. A real pause needs a moderation-hold flag that `reactivate_listing` (and the other lifecycle RPCs) respect; `pause_listing` should be added to `apply_admin_moderation_action` only together with that change. Removal is different: a removed listing cannot be reactivated, republished, archived or edited by its owner through any existing RPC, and the owner has no direct table UPDATE right. Open gap found on 2026-11-13 (read-only inspection of the live definitions): after a removal the owner can still call `save_listing_draft` for the same property, which creates a NEW draft listing, and `publish_listing` accepts it when the property has Tier 3 identity approval and no other active, paused or rented listing (a removed listing is not counted). So the removed listing stays removed, but the property can be re-listed under a new listing. Closing that needs a guard in `save_listing_draft` or `publish_listing` (for example, refuse while the property has a listing removed by moderation), which is a change to live functions and is not part of this migration.

**Removal wording.** The removal confirmation says "This listing will be removed. The owner can't reopen it from the app." It deliberately does not claim the property can't be listed again (see the open gap above).

**Audit tab redesign (2026-11-13).** The Audit tab is a day-grouped list of tappable cards with horizontally scrolling filter chips and "Load more" paging, and each record opens an Audit entry screen (all from `get_admin_audit_log` fields only). Headlines, outcome pills and the "Administrator" actor label come from `AuditPresentation.ts`. Open report/submission/review buttons appear only when that record is already loaded in the session. Details and evidence: [admin-audit-redesign.md](../implementation-reports/ui/admin-audit-redesign.md).

## Reinstate listing and re-listing guard - November 14, 2026 (PREPARED, NOT APPLIED)

**Status:** backend migration `supabase/migrations/20261114120000_admin_reinstate_relist_guard.sql` is prepared and tested locally only (136 container checks, 35 mutations caught). It has not been applied and the app does not use it yet. Ledger entry: ADMIN-REINSTATE-RELIST-GUARD-2026-11-14.

**What it will do.** Close the gap noted above: `save_listing_draft` and `publish_listing` refuse a property that has a removed listing ("Property has a removed listing"). Admins gain `reinstate_listing` in `apply_admin_moderation_action` (removed listing becomes paused, no report, a 10 to 500 character reason, refused if another listing on the property is active, paused or rented, or if the Admin is conflicted on a report about the listing or about its owner); the owner then reactivates with the existing flow. `get_admin_removed_listings` lists removed listings (leaving out any the calling Admin is conflicted on, in count and rows alike), and `get_admin_audit_log` hides the reinstatement row from such an Admin, adds `actorId` and names the subject of verification and report entries.

**Not done in the app.** No Reinstate screen, no message rules for the four new refusals, and the removal wording above is unchanged. Wire these together when the migration is applied. `tests/adminActionsErrorDrift.test.ts` now reads the new audit-log definition and fails if the app and SQL drift.
