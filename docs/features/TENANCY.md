## T1 establishment

Retained T1 source: supabase/migrations/20261110055859_tenancy_establishment.sql, official CLI-created; deployed as 20261110062844. Do not replay its historical local filename. Four new authenticated-only RPCs:

- get_tenancy_establishment(reservation): participant-scoped current context, saved public property summary, exact versions, eligibility, source dates and existing setup.
- establish_tenancy(reservation, operation, property version, identity revision, rent, due day): actual owner only; explicitly reviewed terms; pending_confirmation with only the owner's confirmation.
- respond_tenancy_establishment(reservation, operation, setup revision, property version, identity revision, action): renter confirm, participant activate/cancel, owner review of a changed property.
- get_tenancy_establishment_links(reservation IDs): at most 50 supplied nonnull IDs, participant/relationship-bound reservation-to-tenancy associations.

A new private rentlease_tenancy_setup schema stores unique reservation/tenancy bindings, revision tokens and operation receipts. Tables have RLS with no client access; existing table policies/grants are unchanged. Migration guards stop if existing tenancy RLS/write privileges or required triggers drift. Owner/tenant IDs, property/listing/conversation and dates are derived server-side. Source must remain an effective approved reservation, matching open conversation, active published listing/property, active Tier 1 participants and current exact-property Tier 3 identity. New proposals must begin no later than the reserved move-in date. Property-level locks serialize setup with existing reservation/property/tenancy operations; overlapping open tenancies reject. Unique binding prevents a second setup for the same reservation. Receipts reconcile exact retries; reused operation IDs with different payloads reject.

The owner enters/reviews agreed monthly rent and rent day in a compact existing-pattern setup screen. A landlord action is integrated into approved reservations in the root-composed Chat reservation workspace; both participants can also review from Tenancy. No cross-feature View/ViewModel import was added: App supplies the setup renderer. Renter confirmation is explicit. Same-day confirmation can activate through the existing guarded status update; future confirmed stays remain Upcoming until either participant explicitly starts on/after the start date. Reservation approval/cancellation is never substituted for tenancy confirmation/cancellation. Existing listing sync marks the actual activated listing rented; no payment processing is added.

Current property/identity changes reject stale confirmations. Owner Review updated property explicitly accepts current versions and clears the renter confirmation, requiring review again. Setup revisions prevent stale actions. Pending setup can be cancelled by a participant, without changing its reservation; cancellation is terminal for that source binding, and another setup requires a new approved reservation. General tenancy amendment, termination/renewal and changing an already-proposed rent/period are later scope.
