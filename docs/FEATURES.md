# Feature cohorts

`Scaffolded` means the architectural feature location exists; it does not mean the feature is implemented.

| Feature | Purpose | Status |
|---|---|---|
| Authentication & Profiles | Account identity and profile foundation | Frontend flow implemented; backend auth and persistence pending |
| User Verification | Tiered trust verification | Frontend flow implemented; backend submission, uploads and admin review pending |
| Property & Listing Management | Landlord property and listing workflows | Frontend flow implemented; backend persistence, uploads and maps pending |
| Search & Discovery | Structured filtering, GPS and proximity discovery | Frontend flow implemented; backend search, maps, GPS and proximity data pending |
| Property Recommendations | Content-based property matching | Scaffolded |
| Rental Price Estimation | XGBoost-backed pricing decision support | Frontend flow implemented; FastAPI estimate requests and persistence pending |
| Messaging & Viewing Schedules | Tenant-landlord communication and viewing coordination | Frontend flow implemented; Realtime messaging, uploads and persistence pending |
| Tenancy Management | Structured ongoing rental relationship | Scaffolded |
| Maintenance Requests | Tenant-landlord maintenance coordination | Frontend flow implemented; backend persistence, uploads and notifications pending |
| Ratings & Reports | Reciprocal feedback and reporting | Frontend flow implemented; backend publication, moderation, uploads and persistence pending |
| Admin & Moderation | Platform administration and moderation | Frontend flow implemented; admin authorization, queues, enforcement and audit persistence pending |
| Notifications | In-app and push-notification foundation | Frontend flow implemented; device permission, push delivery and persistence pending |

New implementation goes in `src/features/<feature>/models`, `viewModels`, and `views` as real code is introduced. Empty locations are currently represented by `.gitkeep`; no placeholder screens, ViewModels, models or mock data were generated.

The Authentication & Profiles frontend now includes welcome, sign-in with Home as the first post-login screen, staged registration, email/mobile confirmation presentation, initial profile setup, profile, edit profile, settings, sign-out confirmation, and restricted-account states. New registration proceeds through recommended Matching Preferences before Home. Every account starts as a Tenant; Landlord status is obtained only after completing the verification tiers. Authentication, verification delivery, profile persistence, and document submission remain disconnected until their backend contracts are confirmed.

The User Verification frontend now includes the verification-level overview; Tier 1 email/mobile confirmation; Tier 2 ID selection, local upload preview, review, pending, approved, rejected and resubmission states; and Tier 3 property selection, ownership/authorization document preview, review, pending, approved, rejected and resubmission states. Tier 3 approval promotes the local profile preview from Tenant to Landlord. All submission, file selection, admin decisions and verification outcomes are explicitly presentation-only until confirmed backend contracts are connected.

The Property & Listing Management frontend now includes the landlord-only My Listings dashboard and empty state; a universal safe-area-aware five-item application toolbar shared by Tenant and Landlord workspaces with role-gated Listing/Post actions; listing search, portfolio statistics, tenancy/rent indicators and management actions; the Figma posting-type selection; property creation for photos, basic information, specifications, address/pin, amenities, pricing, description, rules and availability; local photo/cover management; listing preview; incomplete publish requirements; draft and publish presentation states; native listing detail; and edit, pause, reactivate, unavailable and archive management states. Supabase persistence, Storage uploads, MapTiler/MapLibre rendering, geocoding and real publication remain disconnected.

The Search & Discovery frontend now includes the Figma-aligned Tenant property feed; post-registration and profile-editable matching preferences for renter type, stay length, Cavite city, property type, unit specifications, amenities, priority rankings and rental budget; city/location suggestions; list and map result presentations; filters and sorting; current-location permission states; property result cards and details; photo gallery, amenities, nearby places and map-location views; save/unsave and Saved Listings states; and no-results/search-error recovery. Preview listings and local state are used until Supabase/PostGIS search, MapTiler/MapLibre, geocoding, device location, price estimation and Overpass integrations are connected.

The Rental Price Estimation frontend now includes role-aware introduction and property selection; property-information review; explicit local loading presentation; landlord center estimate, suggested range and asking-rent comparison; tenant fair-rent comparison; estimate methodology and disclaimer information; dated estimate history; insufficient-property-data handling; and a retryable error state. Tenants enter through a Discovery property detail and landlords enter through listing detail or management. All figures are clearly presentation-only: the shared FastAPI price-estimation client remains disconnected until the endpoint and request/response contract are confirmed.

The Messaging & Viewing Schedules frontend now includes the role-aware inbox and empty state; conversation search; listing-context conversations; new listing inquiry from a Discovery property detail; message composition; local attachment presentation; viewing introduction, date and time selection, proposal review and pending state; accepted, declined and counter-proposal responses; viewing details and upcoming appointment presentation; cancellation, cancelled and completed states; and handling for listings that are no longer available. The universal Chat toolbar entry opens this shared flow for Tenant and Landlord accounts. Messages, attachment references, viewing proposals and decisions remain local presentation state until Supabase Realtime, Storage, database and notification contracts are connected.

The Maintenance Requests frontend now includes the role-aware request list and empty state; active-tenancy property selection; issue title and description; urgency selection; local maintenance-photo presentation; request review, submission, details and submitted-status tracking; landlord detail, acknowledgement, information request and tenant follow-up; inspection or repair scheduling; scheduled and in-progress states; landlord resolution notes and tenant confirmation or reopening; and landlord rejection with tenant acceptance or dispute. The universal Tenancy tab opens Maintenance for Tenant and Landlord accounts while the dedicated Tenancy Management cohort remains unimplemented. Requests, status changes, schedule data, photo references, decisions and notifications remain local presentation state until Supabase database, Storage, Realtime and notification contracts are connected.

The Ratings & Reports frontend now includes role-aware review availability after a completed tenancy; Tenant-to-Landlord and Landlord-to-Tenant review subjects; interactive star rating and written feedback; confirmation, submission and double-blind publication-waiting presentations; rating summary and published-review cards; confidential report entry for a user, listing or message; target confirmation, categorized reasons, report details and local evidence presentation; final report review and submission; status tracking; moderator requests for more information; and dismissed or action-taken outcome states. Ratings & Reports is accessible from Profile and retains the universal authenticated toolbar throughout its feature screens. Reviews, publication rules, reports, evidence references, moderation decisions and notifications remain local preview state until Supabase database, Storage, server-authoritative eligibility, moderation and notification contracts are connected.

The Admin & Moderation frontend now includes an explicit evaluation-only Admin Preview entry; dashboard workload metrics; combined and dedicated verification/report queues; Tier 2 and Tier 3 verification submission details; local identity and ownership-document viewing; approval, rejection and corrected-information decisions; report details and local evidence viewing; reported user, listing and message context; reporter information requests and report dismissal; proportionate enforcement selection for warning, account restriction, temporary suspension, listing removal and permanent-removal policy preview; decision confirmation; active restriction review and account restoration; admin audit history; and moderation case history. Admin Preview uses its own safe-area-aware Dashboard, Queues, Actions and Audit navigation rather than the Tenant/Landlord toolbar. All admin identity, authorization, queues, documents, evidence, decisions, enforcement, restoration and audit data remain local presentation state until backend-derived admin roles, RLS, secure Storage access, moderation services, immutable audit records and notifications are confirmed.

The Notifications frontend now includes a Profile entry and shared Tenant/Landlord Notification Center; unread and read visual states; mark-all-read behavior; activity categories and day grouping; links into Messages, Viewing Schedules, Maintenance, Verification, landlord Listings, Ratings & Reports and Discovery destinations; an empty state; a local push-permission introduction; a permission-denied recovery state; and an Android push-notification presentation reference. The universal authenticated toolbar remains visible throughout the flow. Notifications, read state and permission choices are local preview data; the existing Expo Notifications service is intentionally not called until device permission timing, Expo project identity, token registration and backend delivery contracts are confirmed.
