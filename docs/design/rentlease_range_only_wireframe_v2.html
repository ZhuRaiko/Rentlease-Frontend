Range-only pricing and one editor

Nobody sees the model's point number. Landlords slide along the typical range and apply the price they pick. Tenants see the same range as a read-only bar. Every card opens the same four-step wizard.

One button per card, one editor behind it

The button names the state. Pause, archive and "Edit property details" live in the three-dot menu, so there is no second Edit button to compare against Create.

Step 1: the estimate inputs come first

Size and rooms sit at the top and say which fields feed the model. The location confirm is one sentence and one button. Amenities get their own card instead of hiding at the bottom.

Price: the range is the product

The ball is hidden until the first touch, so where it starts cannot reveal the middle of the range. It moves in ₱500 steps, with − and + for precision and screen readers.

Review and the tenant view

Review shows one saved notice, an amber verification card and a readable price line. Tenants get the same range as a read-only bar with the listing's rent marked.

Build notes
  • The UI model drops the point estimate where the response is parsed, so no screen can render it.
  • Range ends round outward to ₱500. The ±30% half-width lives in one named constant.
  • The slider is plain React Native with the adjustable role and increment and decrement actions. No native dependency, because the dev client builds locally.
  • Amenities keep saving through the existing property-details call. Only their placement changes.
  • Subtype chips only offer values valid for the chosen type.
  • Published and paused listings save through the existing published-update path, including rent.
